def _is_numeric(value):
    """Return True when value is a real number but not a boolean."""

def dot_product(vector_a, vector_b):
    """Compute the dot product of two equally sized numeric vectors."""
    if not isinstance(vector_a, (list, tuple)) or not isinstance(vector_b, (list, tuple)):
        raise TypeError("dot_product expects both inputs to be lists or tuples.")

    if len(vector_a) != len(vector_b):
        raise ValueError("Vectors must have the same length.")

    total = 0
    for index, (value_a, value_b) in enumerate(zip(vector_a, vector_b)):
        if not _is_numeric(value_a) or not _is_numeric(value_b):
            raise TypeError(
                f"Vectors must contain only real numeric values. Invalid value at index {index}."
            )
        total += value_a * value_b

    return total

def matvec_multiply(matrix, vector):
    """Multiply a matrix by a vector and return the resulting vector."""
    if not isinstance(matrix, (list, tuple)):
        raise TypeError("Matrix must be a list or tuple of rows.")

    if not isinstance(vector, (list, tuple)):
        raise TypeError("Vector must be a list or tuple.")

    if len(matrix) == 0:
        return []

    expected_row_length = len(vector)
    result = []

    for row_index, row in enumerate(matrix):
        if not isinstance(row, (list, tuple)):

        if len(row) != expected_row_length:
            raise ValueError(
                "Each matrix row must have the same length as the vector."
            )

        # Reuse dot_product so that vector validation stays consistent.

    return result

LLM Response: 
Overall

The code is clean, readable, and the validation logic is thorough and mostly consistent. Docstrings are present, errors use the right exception types (TypeError vs ValueError), and matvec_multiply correctly delegates to dot_product rather than duplicating the inner loop. The main problems are a large amount of redundant validation work, a few leftover artifacts, and a demo that doesn't actually verify anything.

Issues worth fixing

1. Leftover prompt comments (high priority)

These three comment blocks are instructions to a code generator, not documentation:

python
# create a function to compute the dot product of two vectors using a for loop
# add comments for the selected function

They describe how the code came to exist rather than what it does, and they'll confuse the next reader. Delete all three pairs; the docstrings already cover the intent.

2. The vector is re-validated once per row

matvec_multiply calls dot_product(row, vector) for every row, and dot_product type-checks every element of both arguments. For the 1000×1000 case in main() that's a million _is_numeric calls on the same vector object, each doing two isinstance checks against an ABC (which is slower than a plain class check). That's likely the dominant cost in the whole program.

Split validation from computation:

python
def _validate_vector(values, label):
    if not isinstance(values, (list, tuple)):
        raise TypeError(f"{label} must be a list or tuple.")
    for index, value in enumerate(values):
        if not _is_numeric(value):
            raise TypeError(f"{label} has a non-real value at index {index}.")


def _dot_unchecked(vector_a, vector_b):
    return sum(a * b for a, b in zip(vector_a, vector_b))

Then dot_product validates both and calls _dot_unchecked, while matvec_multiply validates the vector once up front and each row as it goes. The generator-expression sum is also noticeably faster than manual accumulation with enumerate, since you no longer need the index during the hot loop.

3. main() is a demo, not a test

The docstring says "test" but nothing is asserted — it prints a length and five floats that no one can check by eye. Either rename it to reflect what it does, or add a real check. A cheap one:

python
assert matvec_multiply([[1, 2], [3, 4]], [1, 1]) == [3, 7]

Also add random.seed(...) so runs are reproducible when someone is comparing timings.

4. Empty matrix skips vector validation

matvec_multiply([], "not a vector") returns [] without complaining, because if len(matrix) == 0: return [] fires before anything looks at vector. Validating the vector first makes the behavior uniform. Incidentally, that early return is redundant once you do — the loop already produces [] for an empty matrix.

Smaller things
The row-length ValueError has row_index in scope but doesn't use it, unlike the TypeError directly above. Include the index and both lengths: f"Row {row_index} has length {len(row)}, expected {expected_row_length}."
dot_product's index in the error message is the position within the vector, but when raised from matvec_multiply there's no indication of which row. Adding the row to the message costs nothing and saves debugging time.
Rejecting bool is a defensible choice, but it's user-visible behavior that only appears in the private helper's docstring. dot_product([True], [1]) raising will surprise someone. Mention it in the public docstring.
Accepting only list/tuple rules out range, array.array, numpy arrays, and any custom sequence. If that's deliberate, fine; if not, collections.abc.Sequence (excluding str) is more permissive.
numbers.Real excludes Decimal, which isn't registered under it — worth knowing if decimal inputs are plausible.
No type hints. def dot_product(vector_a: Sequence[float], vector_b: Sequence[float]) -> float: documents the contract better than the prose does.
Naive summation accumulates float error over 1000 terms. Probably irrelevant here, but math.fsum is the fix if accuracy ever matters.
Three blank lines between functions in two places; PEP 8 wants two. No module docstring.
One structural note

If this is headed for anything beyond a teaching exercise, a 1000×1000 matvec in pure Python is roughly a thousand times slower than numpy.dot, and numpy validates dtype once at array construction instead of per element. Worth a comment in the file stating that the pure-Python implementation is intentional, so a future reader doesn't assume numpy was overlooked.
